# Flasher <-> payload protocol (v1)

Реализация: крейт `protocol/` (`flasher-protocol`, общий для флешера и пейлоада, `no_std`, с тестами).

## Как работает пейлоад

1. Флешер заливает UF2 в BOOTSEL-диск. UF2 содержит адреса SRAM (`0x2000_0000..`), поэтому
   загрузчик RP2040 кладёт образ в RAM и запускает его оттуда. **Flash не перезаписывается**
   (в образе нет boot2, vector table лежит в начале SRAM, см. `rp2040-payload/memory.x`).
2. Пейлоад через ROM-функции (`connect_internal_flash`, `flash_exit_xip`, `flash_flush_cache`,
   `flash_enter_cmd_xip`) включает XIP, и flash читается как память по адресу `0x1000_0000`.
3. Пейлоад поднимает USB CDC-ACM (VID `0x2E8A`, PID `0x000A`). На Windows 10+/Linux/macOS это
   штатный класс, драйверы не нужны.
4. Обмен: запрос-ответ, инициатор всегда флешер.

## Транспорт и кадры

Байтовый поток (USB CDC; тот же формат подойдёт для UART). Все числа little-endian.
Кадры самосинхронизируются: приёмник ищет `MAGIC` и валидирует CRC, мусор пропускается.

Запрос (11 байт, фиксированный):

| поле  | размер | описание                           |
|-------|--------|------------------------------------|
| magic | 2      | `B0 07`                            |
| cmd   | 1      | команда                            |
| arg   | 4      | аргумент (индекс блока и т.п.)     |
| crc32 | 4      | CRC-32 по `cmd + arg`              |

Ответ:

| поле    | размер | описание                          |
|---------|--------|-----------------------------------|
| magic   | 2      | `B0 07`                           |
| kind    | 1      | тип ответа                        |
| len     | 2      | длина payload                     |
| payload | len    |                                   |
| crc32   | 4      | CRC-32 по `kind + len + payload`  |

### Команды

| cmd  | имя      | arg    | ответ                                            |
|------|----------|--------|--------------------------------------------------|
| 0x01 | Hello    | -      | `Info` (0x81): version u8, flash_size u32, block_size u32 |
| 0x02 | GetBlock | индекс | `Block` (0x82): index u32 + `block_size` байт данных |
| 0x03 | Reboot   | -      | `Ok` (0x83), затем сброс чипа в прошивку из flash |
| -    | -        | -      | `Error` (0xFF): код u8 (1 = неизвестная команда, 2 = блок вне диапазона) |

### Сценарий

```
Hello                        -> Info{v1, 2 MiB, 4096}
for i in 0..512:
    loop:
        GetBlock(i)          -> Block{i, data}
        crc/index/len ok?    -> break      (иначе повтор GetBlock(i))
Reboot                       -> Ok, устройство перезагружается
```

Таймаут ответа на стороне флешера (рекомендуется 500 мс) трактуется как битый ответ:
запрос повторяется. После N подряд неудач (рекомендуется 5) - ошибка пользователю.

## Принятые решения

- **Устройство без состояния.** `GetBlock(i)` идемпотентен, отдельных ACK/NAK нет: "сумма сошлась,
  дай следующий" = `GetBlock(i+1)`, "не сошлась" = повторный `GetBlock(i)`. Потеря байтов,
  таймауты и перезапуск флешера обрабатываются одним и тем же повтором, ресинхронизация бесплатна.
- **Размер блока 4096 байт** (= flash-сектор, 512 блоков на 2 MiB).
  Один round-trip по USB FS стоит ~1-2 мс, поэтому мелкие блоки (64-256 Б) дают заметный
  накладной расход (десятки тысяч обменов). Крупные блоки (16-64 КиБ) увеличивают цену
  повтора и буфер в RAM без заметного выигрыша. 4 КиБ: ~0.5 тыс. обменов, повтор дёшев,
  буфер кадра ~4.1 КиБ из 128 КиБ RAM. Размер сообщается в `Info`, флешер не должен его хардкодить.
- **CRC-32 (ISO-HDLC, как zlib/PNG)** - выбран вместо суммы/CRC-16/CRC-32C. Простая сумма
  пропускает перестановки и пары ошибок; CRC-16 на блоках 4 КиБ даёт заметно больше шанса
  пропустить ошибку (2^-16) и хуже гарантирует обнаружение; CRC-32 стандартен и есть в каждом
  языке/библиотеке (`crc32fast` на хосте). На Cortex-M0+ табличный CRC-32 ~10 тактов/байт,
  ~0.3 мс на блок при 125 МГц - не узкое место. Аппаратный CRC RP2040 (DMA sniffer) не нужен.
  USB сам защищён CRC-16 на канальном уровне, так что CRC-32 ловит в основном программные сбои
  (переполнение буферов, потеря байтов, рассинхронизация) и защищает от ошибок транспорта UART.
- **CRC кадра покрывает kind/len/index**, а не только данные, а в ответе возвращается индекс блока:
  флешер проверяет, что получил именно запрошенный блок (защита от устаревшего ответа после
  таймаута и повтора).
- **Общий крейт** вместо дублирования констант: формат меняется в одном месте, есть host-тесты.
- **Версия протокола** в `Info`; при несовпадении флешер должен отказаться работать.

## Ограничения и заметки

- Размер flash зафиксирован константой `FLASH_SIZE` (2 MiB). Для других чипов нужно определять
  его по JEDEC ID (команда `0x9F` через SSI) - не реализовано.
- Частота кварца в пейлоаде `12 MHz` (стандарт для Pico и большинства клонов).
- Reboot: полный сброс через watchdog, кроме осцилляторов. Если кнопка BOOTSEL всё ещё
  удерживается при сбросе, загрузчик вернётся в BOOTSEL.
- VID/PID `2E8A:000A` совпадает с CDC-примером pico-sdk; для выпуска продукта нужен собственный.
- Не проверено на реальном железе: корректность запуска RAM-образа из BOOTSEL, скорость обмена.
